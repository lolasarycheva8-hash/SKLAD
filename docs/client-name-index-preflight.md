# Проверка клиентов до новой защиты имён

## Что входит в этот этап

Проверка только читает данные. Она использует тот же PostgreSQL-канонизатор, что API: удаляет U+200B, U+200C, U+200D, U+2060, нормализует Unicode-пробелы и регистр. Отчёт содержит группы, ID, исходные имена, явно показанные невидимые символы, число объектов и заказов у каждого ID и число неоднозначных старых объектов без clientId.

Новый уникальный индекс `clients_name_invisible_normalized_uq` по генерируемому PostgreSQL столбцу `name_canonical` добавлен к декларативной схеме **вместе со старым** `clients_name_normalized_uq`. Столбец вычисляется базой при прямой записи: канонизатор использует `translate` для удаления четырёх невидимых символов и один `regexp_replace` для пробелов; прежнее вложенное `regexp_replace` не возвращено. Выражение непосредственно внутри индекса Publish ошибочно обрезал после первой запятой, поэтому используется столбец и простой индекс. **29 сентября проверен реальный `explainSchemaDiff`:** сначала полное `ADD name_canonical GENERATED ALWAYS AS (...) STORED` (включая все аргументы `translate` и `regexp_replace`), затем `CREATE UNIQUE INDEX ... (name_canonical)`; удалений, структурной потери данных и предупреждений совместимости нет. Это проверка diff, а не применение в production: Publish выполняет пользователь.

## Development: обязательная проверка перед DDL

`pnpm --filter @workspace/db run check:client-names`

Команда завершится с кодом 2 при дублях, 1 при невозможности проверки, 0 при отсутствии конфликтов. Схема и строки не меняются. Обе команды `push` и `push-force` вызывают её **до** drizzle-kit; post-merge использует этот же защищённый путь. При конфликте изменение схемы даже не начинается, старые индексы остаются на месте. Не вызывайте drizzle-kit напрямую в обход проверки.

## Production: перед Publish, а не вместо Publish

Перед выпуском будущего индекса выполните такой же **read-only отчёт в production** через разрешённый доступ к production-БД. Не подставляйте production credentials в development, не запускайте push, DDL или исправляющий SQL в production из shell. Встроенная проверка development не подтверждает чистоту production.

Чтобы получить точный SELECT из общего канонизатора без подключения к БД: `pnpm --filter @workspace/db exec node ./scripts/check-client-name-conflicts.mjs --print-sql`. Выполните этот SELECT через разрешённый read-only доступ с явно выбранной средой production. Непустой результат запрещает переход к установке индекса; ошибка проверки — тоже, а не «конфликтов нет».

Replit Publish самостоятельно строит и применяет разницу схем. Этот проектный preflight не является перехватчиком внутренней миграции Publish и не обещает её атомарность. При непустом отчёте сначала исправьте данные через опубликованные административные операции и заново проверьте production; даже при пустом отчёте перед выпуском отдельно проверьте diff нового индекса. Не добавляйте DDL в build или startup.

В период финальной проверки и установки защиты исключите прямые записи в БД в обход API; при необходимости согласуйте окно обслуживания. Read-only снимок не блокирует последующие внешние записи.

## Управляемое исправление: переименование по ID

1. Сохраните отчёт и проверьте принадлежность объектов/заказов каждого ID. Одинаковое визуальное имя не доказывает, что это одна организация.
2. Администратор выбирает осмысленные **различные** имена, а не ещё один невидимый символ. Используйте существующую форму переименования клиента (PATCH по его ID). Не удаляйте, не объединяйте и не переназначайте клиентов автоматически.
3. Если все объекты имеют clientId, переименование одного ID обновляет только его отображаемые имена объектов в одной транзакции. ID объектов и клиентов, а также ссылки заказов остаются прежними.
4. Если есть старые объекты без clientId с неоднозначным именем, операция отклоняется. Сначала администратор должен установить их принадлежность по документам и назначить правильные ID через поддерживаемую форму объекта. Не распределяйте такие строки по совпадению имени.
5. Если записи действительно обозначают одну организацию, остановитесь: слияние со всеми связями требует отдельного согласованного плана. Переименование не является слиянием.
6. Повторите read-only проверку: только пустой список конфликтов допускает следующий этап. Перед будущим индексом проверьте сам diff Publish и наличие резервной копии. Выполнять Publish должен пользователь.

Интеграционные проверки используют только изолированные временные схемы с историческими дублями; ограничения рабочих таблиц для теста не снимаются.

Запуск всего набора для этого этапа: `pnpm --filter @workspace/api-server run test:client-name-rollout`.
